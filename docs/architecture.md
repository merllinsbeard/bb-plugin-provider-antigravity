# Architecture: `bb-plugin-provider-antigravity`

## Goal and constraints
Register Google Antigravity (`providerId: "antigravity"`, `pluginId: "provider-antigravity"`) as a BB ACP provider whose live account quota appears in both `bb settings usage` (`system.usageLimits` -> host bridge `provider/usage`) and `bb--provider-usage` on desktop and mobile (`provider-usage.v1.listResources` / `getResource`). Existing threads on `acp-antigravity` (`provider-acp`) must remain untouched.

## Why native print-mode JSON replaced PTY
Live verification on `agy 1.5.15` showed that the documented non-interactive command:

```bash
agy -p "/usage" --output-format json --print-timeout 15s </dev/null
```

completes in ~1.8 s (`exit 0`, `num_turns: 0`, `total_tokens: 0`, `conversation_id: ""`), returns structured JSON (`command.data.groups[].buckets[]` with `id`, `name`, `window`, `remaining_fraction`, `reset_time`), and works even when interactive TUI onboarding has not been completed (`onboardingComplete: false`).

We therefore ship only the native print-mode JSON reader and drop the PTY/TUI layer (no Python helper, no `@xterm/headless`, no screen pagination, no interactive ToS exposure). If a future `agy` release disables print-mode slash expansion, `command` disappears from the JSON envelope and the reader returns a clear, immediate `error` naming the cause.

## Design decisions
- **Reader & caching:** Native print-mode JSON reader producing pure domain types (`ProviderQuota` -> `QuotaWindow[]`), with zero host TTL cache and a server-side 60 s cache plus in-flight deduplication in `src/usage-source.ts`.
- **Omitted flags:** `reasoningCli: --effort` is intentionally omitted because `agy acp` does not accept it.
- **Contract & robustness details:**
  1. Forward `refresh` into `bb.sdk.system.usageLimits({ hostId, providerId, refresh })`.
  2. Clamp `usedPercent` to `0..100` (`Math.min(100, Math.max(0, round1((1 - remaining) * 100)))`) to match the bridge `providerUsageWindowSchema` contract.
  3. Resolve `agy` via `BB_ANTIGRAVITY_EXECUTABLE` -> `experimental_hostToolchain.resolve("agy")` -> `~/.local/bin/agy`, checking executable permission (`X_OK`).
  4. Preserve provider bucket IDs (`gemini-weekly`, `gemini-5h`, `3p-weekly`, `3p-5h`, `gemini-argon-wtu-weekly`) through bridge passthrough into `usage-source.ts` (fallback `${index}:${label}`).
  5. Keep `kind: "custom"` with concise period-first labels (`7d · Gemini`, `5h · Gemini`, `7d · Claude/GPT`, `5h · Claude/GPT`, `7d · Argon`) so `bb settings usage` and `bb--provider-usage` show identical text, React keys never collide, and narrow sidebar/mobile rows never truncate the period.
  6. Keep in-process `withSingleFlight` around `probeQuota` in `host.ts` so concurrent `bb settings usage --refresh` and `bb--provider-usage` calls share one `agy` process.
  7. Never read or log token contents (`existsSync` presence check on `~/.gemini/antigravity-cli/antigravity-oauth-token` avoids `agy`'s 60 s interactive OAuth wait); `readAccount()` never spawns.

## Account pool: one Antigravity account per thread
Several Google accounts serve BB as the one `antigravity` provider. Each thread is bound to one account when it first starts and stays on it, because agy keeps conversation history per account.

### Pieces
- **Accounts** (`src/pool/account.ts`). The built-in `default` account is the existing `~/.gemini/antigravity-cli`, used without any bind. Every added account is a folder `~/.local/share/agy-accounts/<name>/` (`AGY_POOL_ACCOUNTS_DIR` overrides the root). An account without `antigravity-oauth-token` is unauthenticated and never picked.
- **Bindings** (`src/pool/bindings.ts`). `~/.local/state/agy-pool/bindings.json` (`AGY_POOL_STATE_DIR` overrides) maps `threadId -> { account, pid, boundAt }`. It is written atomically (temp file and rename) under `flock` on `bindings.lock`, so two threads that start together see each other's choice. It lives outside BB's plugin data directory because the launcher and `agy-pool list` run outside the plugin process, and because BB deletes plugin files on uninstall while the account folders and the conversations they hold survive.
- **Pick** (`src/pool/pick.ts`). A model group counts when it has both a 5-hour and a weekly bucket (today Gemini and Claude/GPT; the weekly-only Argon group does not count). Its value is the smaller remaining fraction of the two, and an account scores the mean across those groups (0 when every group is exhausted). The highest score wins; a tie goes to the account with fewer live threads (bound pid alive and its `/proc/<pid>/environ` carries that `BB_THREAD_ID`). An account whose quota could not be read ranks below every account with known room. When every account scores zero, the launcher exits 1 naming the nearest reset. With a single signed-in account the launcher binds it without probing, so a one-account machine starts threads as fast as before.
- **Quota per model family** (`src/pool/family.ts`, `src/pool/exhaustion.ts`). agy meters Gemini models, Claude/GPT models and (on Pro plans) Gemini Argon in separate groups, so an account out of one group still serves the others. A thread starts before its model is known, so the first pick uses every group as above. The relay learns the session's model from agy's session answers (`configOptions` model, else `models.currentModelId`) and bb's `session/set_config_option` or `session/set_model`. When the model is unknown, a refusal still moves the thread off the refusing account without marking any family. When agy refuses a prompt for quota, the relay marks that account out of that family only, in `~/.local/state/agy-pool/exhausted.json` until the reset agy named, and asks for an account with room in that family, ranked by that group's windows alone. A prompt whose family is already marked out on the thread's account moves before it is sent. "Out of quota" reaches bb only when every account is out of that family, and then as a failed turn: the relay answers the prompt with a JSON-RPC error carrying the message `cli.ts resolve` printed (`agy-pool: every Antigravity account is out of <family> quota. The nearest reset is <time> (account "<name>").`, the same words a thread that cannot start gets), so the thread lands in `error` instead of `idle`. When the move itself fails (the new account errors on `initialize` or `session/load`), the error names the refusing account, the target and the target's error.
- **Hand-off** (`src/quota-handoff.ts`). The server listens for `thread.failed` and reads the newest `provider/error`, `system/error` or `client/turn/requested` event: bb records a failed prompt as `provider/error` (message "Provider error", the relay's text in `detail`) and a failed start as `system/error`, and a turn request on top means the latest turn left no error, so an exhaustion error from an earlier turn never counts. When that error's message or detail is the pool message and the thread is visible, top level and not started by a plugin, it spawns a thread with the `quotaHandoff*` settings (Claude Code, Opus 5.5, Medium by default) in the same environment and permission mode, prompted `Continue from @thread:<id>` and one sentence naming the exhausted family and reset. It records `quotaHandoff: { failureEventId, successorThreadId }` in the failed thread's plugin metadata before and after the spawn, so one failure yields at most one successor across reloads.
- **Launcher** `bin/agy-pool`, set as `acpLaunchSpec.command` by absolute path (resolved from the bundle's `import.meta.url`). It is bash so it can `exec` the final command: agy (or bwrap) keeps the launcher's pid, stdio, and exit code. The decision runs in `src/pool/cli.ts` under `/usr/bin/node`, which strips TypeScript types natively; that is why relative imports use `.ts` paths. `AGY_POOL_ACCOUNT=<name>` forces an account and records no binding; without `BB_THREAD_ID` the launcher uses `default`. Overhead is about 0.3 s per thread start (measured: `agy-pool --version`).
- **Commands.** `agy-pool login <name>` creates the folder, copies `settings.json` from the default account, and runs `agy acp --login` inside the bind. `agy-pool list` prints every account with its sign-in state, quota windows, bound thread count, and live thread count as JSON.
- **Usage card** (`src/usage-source.ts`, `host.ts`). The plugin's discoverable usage source lists one resource per pool account, so bb's usage panel draws each account as its own block: the header is the Google address from `id_token_email` in the account's token file, the badge is the pool name and route (`acc2 · proxy`, `default · direct`), and the window labels carry no account prefix. The server gets the account list and each account's quota from the plugin's host entry (`src/pool-host-contract.ts`): `listAccounts` reads folders only, `readAccountUsage` probes exactly one account through its own route. An account that is not signed in or has a broken proxy file shows an error naming it and the `agy-pool login` command. The server keeps each account's reading for 60 s. The app adds a dashed line between two accounts of one provider through a content script (`app.ts`), because the card itself separates providers only. The provider's own `provider/usage` answer (`src/usage/dialect.ts`) still merges every account with name-prefixed windows for other consumers.

### Isolation: narrow bind, verified on Linux with agy 1.5.15
- `bwrap --dev-bind / / --bind <account> ~/.gemini/antigravity-cli agy ...` with an empty folder makes agy ask for a Google sign-in, so the narrow bind separates accounts. `~/.gemini/config` (MCP, hooks, skills) and `~/.gemini/AGENTS.md` stay shared: agy populated the empty account's `mcp/` from the shared config on first start. `HOME` stays intact, and `git config user.name` inside the bind matches the host's.
- agy's native `--app-data-dir` was checked first. `agy acp` accepts it, but it joins the value under `~/.gemini` and print mode rejects the flag (exit 2), and the quota probe needs print mode. bwrap covers both modes with one mechanism.
- `agy --sandbox` still works inside the bind: a command run by agy's terminal tool sees `/etc` as a read-only file system and 175 mounts, against `Permission denied` and 136 mounts inside the same bind without `--sandbox`.
- Process lifetime. bwrap stays the parent of agy and does not forward signals, but BB starts ACP agents in their own process group and stops them with SIGTERM to the leader, then SIGTERM to the whole group, then SIGKILL (`stopProcessGroupLeaderFirst` in the SDK). agy inside the bind therefore receives SIGTERM and shuts down cleanly; `tests/pool.test.ts` replays that sequence. `--die-with-parent` is deliberately absent because it would SIGKILL agy before the group SIGTERM arrives.

## Per-account proxy
Every account normally reaches Google from the server's one datacenter IP, which lets Google link the accounts. An account can instead own a fixed proxy, and then all of its Google traffic leaves through that proxy.

- **The file.** `agy-pool-proxy` in the account folder (for `default`, in `~/.gemini/antigravity-cli`) holds one proxy URL (`http`, `https` or `socks5`, credentials allowed), mode 0600. The name is prefixed because agy owns that folder. No file means the account goes direct, exactly as before. The folder is read once in `src/pool/egress.ts`, and the account's type carries the result: direct, proxy, or unusable. Only a usable account can produce an agy command (`accountCommand` takes `UsableAccount`), so an unreadable or malformed file can never fall back to direct.
- **The environment.** `accountCommand` is the one place every agy launch is built (launcher, `login`, quota probe, usage card), and for a proxied account it adds `HTTPS_PROXY` and `HTTP_PROXY` set to the URL and `NO_PROXY=localhost,127.0.0.1,::1,100.64.0.0/10,.ts.net`, so loopback MCP servers and tailnet hosts stay direct. agy has no proxy setting of its own; it honours these variables (Go's standard proxy handling). The launcher exports them in bash before `exec`, so the URL and its password never appear in the argv of bwrap or agy; the probe merges them over the sanitized inherited environment.
- **The probe goes through the proxy too.** The usage card probes every account about once a minute and the launcher probes before a pick, so a probe outside the proxy would show Google the server IP for that account. It uses the same command as the launch.
- **Fail closed.** With the proxy down agy exits 1 (`proxyconnect tcp: ... connection refused`) and opens no direct connection. The pool already ranks an account whose quota could not be read below the rest, so new threads go to working accounts. An account with a malformed file is never picked; a thread already bound to it, or `AGY_POOL_ACCOUNT` naming it, stops with the file's problem instead of starting.
- **Commands.** `agy-pool login <name> --proxy <url>` saves the file first, asks `http://ip-api.com/json` through it (curl reads the proxy from its config on stdin, not argv) and prints the exit IP and country, stops if that fails, and only then runs the sign-in through the proxy, so the token is issued to the proxy's IP. `agy-pool list` shows each account's `egress` as `direct`, `proxy host:port` (no credentials) or `unusable`, next to the quota error.
- **What stays direct.** MCP servers agy starts carry no Google token and are outside the scope. Local and tailnet ones are covered by `NO_PROXY`. Node-based remote MCP bridges that use Node's `fetch` without `NODE_USE_ENV_PROXY=1` ignore `HTTPS_PROXY` and reach their remote host from the server IP. Commands agy's terminal tool runs inherit the proxy variables.

### Live evidence on Linux with agy 1.5.15
`node scripts/live-proxy-check.ts` runs the plugin's own quota probe for `default` with a temporary `agy-pool-proxy` pointing at an in-process CONNECT proxy that requires a password, polls `ss -tnp` every 50 ms for the probe's whole process tree, then repeats with the proxy port closed and removes the file. On 2026-11-23 it read all five quota windows through the proxy; the tunnels were `daily-cloudcode-pa.googleapis.com`, `aicode.googleapis.com`, `www.googleapis.com`, `play.googleapis.com`, `lh3.googleusercontent.com` and remote MCP hosts. The agy process had no direct public connection in either run, and with the port closed the probe failed instead of going direct. The only direct public connection observed in the tree was a Node-based remote MCP bridge as described above. The probe spends no model tokens (`num_turns: 0`). A connection shorter than the 50 ms poll could be missed by `ss`; the fail-closed run covers that gap, since agy reached nothing at all without the proxy.
